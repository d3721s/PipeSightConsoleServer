## 优先处理的可靠性和正确性问题

**1. P1：FFmpeg 的 stderr 管道无人读取，录像可能在长时间运行后停住。**

位置：[recorder_service.py:150](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/recorder_service.py:150)。静态确认。

`Popen(..., stderr=subprocess.PIPE)` 后没有消费者，也没有设置抑制正常进度输出的日志参数。输出填满系统管道时，FFmpeg 会阻塞在写日志上，进程仍存活，`state.active` 也可能继续为真。停止流程还会先 `wait()`，最终可能被迫 terminate/kill。

建议：继承 systemd 的 stderr，或者启动持续读取 stderr 的线程，并仅保留有界日志尾部用于展示错误。长期运行的日志消费者需要随录像进程一同关闭。Python 官方文档说明了 [PIPE 无人消费时的阻塞条件](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.wait)。

**2. P1：录像启动和结束没有互斥保护，并发请求可创建两个录像进程。**

位置：[recorder_service.py:81](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/recorder_service.py:81)、[recorder_service.py:183](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/recorder_service.py:183)。模拟依赖复现。

`if self.state.active` 与后续设置 active、创建进程之间存在窗口。两个同步 API 请求可以在不同线程同时通过检查，覆盖共享 `_process`、工作线程和输出配置。隔离复现中两个启动均成功，输出目标相同。状态接口也可能触发 `_finish()`，与 stop 或分段工作线程交错执行。

建议：用明确的 idle/starting/recording/stopping 状态机和生命周期锁串行管理启动与停止；为每次录像建立独立上下文和唯一输出标识。锁内避免等待需要同一锁的后台线程，进程退出和分段收尾应只执行一次。

**3. P1：一个慢客户端可以阻塞 C++ 相机回调和其他观看者。**

位置：[ws_server.h:136](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/pointcloud_bridge/ws_server.h:136)、[ws_server.h:213](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/pointcloud_bridge/ws_server.h:213)、[main.cpp:112](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/pointcloud_bridge/main.cpp:112)。静态确认，设备时延待实测。

广播在 `clientsMtx_` 锁内遍历客户端，并通过阻塞 socket 的 `sendAll()` 写完整大帧，没有发送超时或独立发送队列。该函数直接从 SDK 回调调用。某个平板网络变慢、暂停读取或消失时，发送缓冲区填满后会阻塞同一广播中的其他客户端；同一相机回调内的其他图像类型也会等待。握手中的阻塞 `recv()` 同样没有超时，可占住 accept 线程。

建议：SDK 回调只提交最新帧，由独立 I/O 循环发送；每个客户端采用有界队列并丢弃尚未开始发送的旧帧，限制握手和发送时间。非阻塞发送需要正确维护已经部分发送的帧，不能直接截断 WebSocket 帧。同时将跨线程 `running_` 改成原子状态，完善 Close/Ping 处理。

**4. P1：断线时积累并重放旧运动指令，后端也缺少指令新鲜度约束。**

位置：[ws.ts:57](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/front_end/src/ws.ts:57)、[modbus_service.py:129](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/modbus_service.py:129)、[modbus_service.py:293](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/modbus_service.py:293)。队列重放已模拟复现，硬件后果未实测。

**5. P1：旧 WebRTC 连接任务的异常会关闭新连接。**

## 性能优化的主要工作

**8. P2：媒体列表存在隐藏的 N+1 配置查询。**

位置：[media.py:31](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/api/media.py:31)、[media.py:137](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/api/media.py:137)、[config.py:112](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/config.py:112)。真实数据库复现。

每行调用 `_storage_url()`，该函数读取 `settings.active_storage_dir`，从而创建新的 Session 并查询 storage 设置。普通照片 N 行对应 N+1 次 SQL；有深度文件或视频轨迹时可能接近 2N+1。报告图片和标注列表也使用相同模式。`get_settings()` 的 lru_cache 仅缓存 Settings 对象，未缓存这个 property 的查询。

建议：先统一第 7 项的运行时路径，再让 URL 转换成为接受已解析根目录的纯函数；每个请求只获取一次根目录。避免在逐行转换中 mkdir、resolve 根目录和访问配置数据库。

**9. P2：每次拍照都同步加载所有媒体并扫描文件系统。**

位置：[media.py:79](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/api/media.py:79)、[storage_service.py:255](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/server/app/services/storage_service.py:255)。真实数据库/文件系统复现。

**12. P2：有效点数变化时频繁替换 GPU 属性，资源释放不及时。**

位置：[PointCloudViewer.vue:149](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/front_end/src/components/PointCloudViewer.vue:149)、[main.cpp:189](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/pointcloud_bridge/main.cpp:189)。真实 Three.js 模块与模拟 GL 复现。

C++ 过滤无效点后，每帧 count 可以变化。前端只在长度完全相同时复用 position/color；点数改变就创建两组新属性。对当前 Three.js 的模拟验证中，100 帧交替点数创建 200 个 GL buffer，没有显式删除旧 buffer；最后 dispose 只删除当前 2 个。实际显存回收还受浏览器 GC/驱动影响，因此尚不能断言显存必然无限增长，但分配和上传抖动是确定的。

建议：按协议上限预分配 position/color 数组，用 `setDrawRange()` 表示有效点数，只上传有效范围；超出容量时有步骤地释放旧 geometry。颜色可按 z 在 shader 中计算，减少 CPU 遍历和颜色上传。动态几何还需更新包围体，或明确处理 frustum culling，避免沿用首次点云的包围球。

`renderFrame()` 还会在等待 66 ms 数据应用间隔时重复 render，并在处理一帧后额外调度一次。建议区分数据待处理、控件变化和画布尺寸变化，只在需要时重绘；DPR 上限应结合平板 GPU 实测。

**13. P2：报告/录像状态同步的 4 秒超时实际无效。**

位置：[session.ts:149](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/front_end/src/stores/session.ts:149)、[session.ts:162](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/front_end/src/stores/session.ts:162)、[api.ts:75](C:/Users/runyu/Desktop/yb_ws/PipeSightConsoleServer/front_end/src/api.ts:75)。模拟 fetch 复现。

**16. 图像捕获与传输存在较多复制、编码和带宽开销。**

普通照片先编码 PNG data URL，再通过 Image 解码、绘制 OSD、再次编码 PNG，最后 base64 JSON 上传。深度快照也有同样的 OSD 路径，实时深度每帧额外复制 raw 数组，RGB/IR 每帧在主线程转换 RGBA。原始 RGB 不压缩；例如 1280×720×3×15 fps 约 41.5 MB/s、332 Mbit/s，实际带宽取决于设备输出分辨率和帧率。

建议：直接在一次 Canvas 绘制中合成 OSD，再用异步 toBlob 和二进制上传；保持原始深度的无损精度。实时 RGB 可以评估摄像端 JPEG/视频编码、降分辨率和按需帧率；深度着色和像素转换可通过 Worker/OffscreenCanvas 或 WebGL 减少主线程占用，需用 Performance trace 验证。

录像使用 drawtext + libx264，包含解码、滤镜和重新编码。若 OSD 是产品要求，单纯改成视频 copy 会失去烧录 OSD；应比较设备上的硬件编解码、滤镜兼容性和画质。若提供无烧录模式，可保留原流与独立元数据，作为另一种明确的录像选项。

实时巡检页面访问后保持视频连接并继续解码，这是当前针对 Android 返回页面的设计取舍。需要同时测试二维视频后台运行与三维页面前台运行的 CPU/GPU；采用可配置的后台降载或延迟释放，并验证返回页面体验。

## 建议的实施顺序与验收

1. 先修录像 stderr 消费和生命周期竞态、控制指令过期、WebRTC 切源和深度同帧捕获。加入能覆盖这些异步边界和失败场景的回归测试。
2. 统一运行时存储路径，消除逐条配置 SQL，补齐附属文件占用，改用合并的后台配额清理；引入分页、索引和已有数据库迁移。
3. 点云固定容量缓冲、广播 I/O 与 SDK 回调分离，修复状态同步超时；验证慢网络、客户端离开和多客户端并存。
4. 用车载设备与目标平板采集 Performance trace、录像 CPU、串口时延和链路带宽，再决定图像压缩、Worker、硬件编码及前端依赖裁剪的具体方案。
